# Root-Cause Tracing

실패가 파일이나 경계를 둘 이상 넘을 때 쓴다.

## 소리가 아예 안 난다

이 순서로 추적한다:

```text
사용자 제스처 -> AudioContext 생성 -> ctx.state -> 샘플/악기 로드 -> 스케줄러 틱
  -> 구간 안 노트 조회 -> 노드 생성 -> 그래프 연결 -> 마스터 게인 -> destination
```

확인:

- `ctx.state`가 `'running'`인가. `'suspended'`면 여기서 끝이다 — 사용자 제스처 핸들러 안에서 `resume()`을 호출해야 한다. **무음 버그의 1순위.**
- 모듈 스코프에서 `new AudioContext()`를 하지 않았는가. SSR에서 깨진다.
- 스케줄러 틱이 실제로 돌고 있는가. 틱 안에 로그를 하나 찍어 본다.
- 틱이 찾는 구간에 노트가 실제로 있는가. 시작 커서가 곡 끝을 지나 있지 않은가.
- 노드가 `destination`까지 연결됐는가. 중간 게인 노드를 만들고 연결을 빠뜨리는 경우가 많다.
- 마스터 게인이 0은 아닌가. 트랙이 뮤트거나 다른 트랙이 솔로 상태는 아닌가.
- 샘플 기반이면 `AudioBuffer`가 실제로 디코드됐는가. 로드 실패가 조용히 삼켜지지 않았는가.
- 예약 시각이 이미 지난 과거는 아닌가. 과거 시각으로 `start()`하면 즉시 울리거나 무시된다.

## 박자가 밀리거나 흔들린다

```text
노트의 정수 틱 -> 템포로 초 변환 -> 예약 시각 계산 -> 실제 예약 -> 오디오 하드웨어
```

확인:

- **`setTimeout`이나 `rAF`로 노트를 직접 울리고 있지 않은가.** 이게 거의 항상 원인이다. 두 타이머는 메인 스레드에 묶여 수십 ms씩 밀린다.
- 예약 시각이 `ctx.currentTime` 기준 절대값인가. `Date.now()`나 `performance.now()`가 섞이면 두 시계가 서로 다르게 흘러 점점 벌어진다.
- lookahead가 충분한가. 틱 간격보다 짧으면 구멍이 생긴다.
- 재생 위치를 `pos += delta`로 누적하고 있지 않은가. 부동소수 오차가 몇 분 뒤 들리는 수준으로 쌓인다.
- 노트가 초 단위로 저장돼 있지 않은가. **템포를 바꾼 뒤에만 어긋난다면 이게 원인이다.**
- 재생 중 메인 스레드가 막히지 않는가. 큰 배열 정렬, 대량 리렌더, 레이아웃 스래싱이 틱을 지연시킨다.
- 플레이헤드 렌더가 React 상태를 거치고 있지 않은가. 매 프레임 리렌더가 오디오까지 끌어내린다.

## 소리가 끊기거나 지직거린다

```text
동시 발음 수 -> 노드 생성/정리 -> 합산 진폭 -> 메인 스레드 부하 -> AudioWorklet process()
```

확인:

- 합산 진폭이 1.0을 넘지 않는가. 악기 5종이 겹치면 쉽게 넘고, 그게 "깨지는" 소리로 들린다. 마스터 게인 스테이지를 먼저 본다.
- 동시 발음 상한이 있는가. 드럼 연타나 코드 스트로크에서 보이스가 무제한으로 늘면 CPU가 튄다.
- **노드가 정리되고 있는가.** `disconnect()` 누락은 "처음엔 괜찮은데 몇 분 뒤 느려지고 끊김" 증상으로 나온다. 재생을 오래 걸어 두고 확인한다.
- `start()`한 노드를 재사용하고 있지 않은가. 일회용이다.
- AudioWorklet의 `process()` 안에서 할당하고 있지 않은가. GC가 돌면 버퍼를 놓친다.
- 재생 중 무거운 동기 작업이 도는가.

## 편집한 게 안 들린다

```text
편집 UI setState -> 곡 데이터 교체 -> 엔진이 읽는 시점 -> 이미 예약된 구간
```

확인:

- 상태 setter가 **새 객체**를 만들었는가. `useState`에 담긴 객체를 제자리에서 변형하면 React Compiler가 관찰하지 못한다.
- 엔진이 곡 데이터를 언제 다시 읽는가. 스케줄러가 매 틱 최신 데이터를 보는가, 아니면 재생 시작 시 스냅샷을 뜨는가.
- **이미 lookahead 구간 안으로 예약된 노트는 그대로 울린다.** 편집이 다음 틱부터 반영되는 것은 정상 동작일 수 있다 — 버그로 단정하기 전에 설계 의도를 확인한다.
- 드래그 중 미리보기만 갱신하고 커밋을 `pointerup`에서 하는 구조라면, 커밋이 실제로 일어났는가.

## 빌드, 타입, 린트 실패

```text
첫 에러 -> 소유 파일 -> import/타입 사슬 -> 최근 diff -> 같은 패턴의 동작하는 파일
```

확인:

- 뒤따르는 연쇄 에러를 쫓기 전에 **첫 번째** 에러를 본다.
- `AudioContext is not defined` / `window is not defined`: 서버에서 평가되는 코드다. 모듈 스코프 생성이나 `use client` 누락.
- Web Audio 타입: `AudioContext` vs `BaseAudioContext`, `webkitAudioContext` 폴백 타입 처리.
- `.next/` 캐시나 생성된 `next-env.d.ts`가 얽혀 있는지.
- 같은 패턴을 쓰는 가장 가까운 동작하는 파일.

## Stop Conditions

멈추고 가설을 다시 세울 때:

- 두 번 고쳐서 실패했을 때.
- 가설이 더 이상 근거를 설명하지 못할 때.
- 수정이 요청과 무관한 광범위한 아키텍처 변경을 요구할 때.
