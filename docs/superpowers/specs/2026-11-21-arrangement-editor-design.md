# 블록 조립 편집 UI와 곡 모델 v3 (하위 프로젝트 2a)

작성일: 2026-11-21
상태: 설계 승인됨, 구현 계획 전

재구상(`2026-11-20-core-model-sample-engine-design.md`)의 **하위 프로젝트 2**를 둘로 나눈 것 중 **2a — 블록 조립**이다. 비전공자가 코드 진행과 악기별 패턴을 조립해 곡 뼈대를 만들고 들어 보는 화면과, 그 화면이 기대는 곡 모델 변경(v3)을 다룬다. **음 단위 편집(피아노롤)은 2b**이고 이 문서의 범위 밖이다.

## 1. 결정 요약

## 2. 범위

**한다:** 곡 모델 v3(진행, 패턴 클립), 그에 맞춘 검증·스키마·펼치기·베이크·데모·테스트, 순수 편집 함수(`lib/score/edit.ts`), 상태 계층(`state/`), 편집 화면(`components/studio/`), 자동 저장, `/`를 편집 화면으로 교체.

**하지 않는다:** 음 편집·피아노롤·클립 복사/붙여넣기·다중 선택, 트랙 추가·삭제·악기 변경, 마디 단위 외의 박자표(4/4만), 다시실행, 루프·시크·줌, 파일 열기·저장, 링크 공유, 오디오 내보내기, 복잡한 드럼 편집. 기존 소리 확인 화면(`VerifyScreen`)은 편집 화면이 대체하므로 지운다.

## 3. 곡 모델 v3 (`lib/score/`)

### 3.1 타입

```text
Song         { v: 3, tempo, timeSignature, bars, progression: ChordSegment[], tracks, meta }
ChordSegment { start, length, chord }        // 곡 전체를 빈틈·겹침 없이 덮는 분할
PatternBody  { type: "pattern", pattern }     // 옛 ChordBody에서 chord 필드가 빠진다
NotesBody    { type: "notes", notes }         // 변경 없음
```

- `SONG_VERSION`은 3이다. v2 곡은 **거부**한다(공개된 곡·링크가 없어 마이그레이션하지 않는다).
- `ChordBody`는 `PatternBody`가 된다. 드럼 클립은 더 이상 쓰이지 않는 가짜 코드 필드를 가질 필요가 없다.
- 새 곡의 진행은 곡 전체를 덮는 C maj 한 구간이다.

### 3.2 불변식 (`validateSong`)

- 진행은 최소 한 구간이고, `start` 오름차순으로 `0`에서 `bars × ticksPerBar`까지 **빈틈과 겹침 없이** 이어진다(`segments[0].start === 0`, `s[i].start + s[i].length === s[i+1].start`, 마지막은 곡 끝).
- 구간의 `start`·`length`는 정수이고 `length ≥ 1`이다. 코드는 `root` 0..11 정수와 닫힌 `quality` 열거다(**`validateSong`이 코드를 검사한다** — 지금까지는 zod만 보아서 타입 밖 `quality`가 `chordPitch`에서 터졌다).
- UI 편집 함수는 구간 길이를 반마디 이상으로 유지하지만, **모델의 불변식은 `length ≥ 1`까지만** 요구한다(손으로 고친 파일이 반마디 미만이어도 거부하지 않는다).
- 새 이슈 코드: `progression-invalid`(비어 있음·시작이 0이 아님·빈틈·겹침·곡 끝 불일치), `invalid-chord`. 기존 코드 중 `unknown-pattern`·`pattern-instrument-mismatch`는 `pattern` 본문에 그대로 적용한다.

### 3.3 펼치기 (`expandSong`)

- 화음 악기의 `pattern` 클립: 패턴 반복과 스텝 시각은 그대로(클립 끝에서 자름)이고, 각 스텝의 **음높이는 그 스텝의 절대 시각(`clip.start + 반복 시작 + step.at`)에 해당하는 코드**를 진행에서 찾아 `chordPitch(chord, degree, octave)`로 정한다.
- 그래서 코드를 바꾸면 모든 트랙이 따라오고, 마디 중간에서 코드가 바뀌어도 패턴이 끊기지 않고 **그 시각부터 새 코드로 이어진다.** 이미 울리기 시작한 음은 코드 경계를 넘어도 높이를 유지한다.
- 드럼 `pattern` 클립은 진행을 읽지 않는다. `notes` 클립은 변경 없다.
- 진행 조회는 `chordAt(progression, tick)` 순수 함수이다(이분 탐색). 진행이 곡을 덮는다는 불변식에 기대므로, 못 찾으면 예외를 던진다(검증된 곡에서는 일어나지 않는다).
- **베이크:** 패턴 클립을 음 클립으로 바꿀 때는 **그 시점의 진행으로 펼친 음**을 굳힌다. 그 뒤에는 코드를 바꿔도 따라오지 않는다(기존 결정 그대로). `bakeClip`/`clipNotes`의 시그니처에 클립 시작과 진행이 추가된다.
- 재생과 내보내기가 같은 `expandSong`을 쓴다는 규칙, 이벤트 시간순(안정 정렬)은 유지한다.

### 3.4 스키마와 복구 (`parseSong`)

- `v: 3`만 받는다. `progression`은 구조 검증(zod)에서 최소 1개 구간 배열이다.
- 복구: 진행 구간의 소수 틱은 클립과 같이 끝점 기준으로 반올림하고, `start` 순서가 어긋나면 정렬한다.
- 거부(복구하지 않음): 진행이 곡을 덮지 못함(빈틈·겹침·시작/끝 불일치), 알 수 없는 코드 종류·패턴·악기·버전. 정책은 기존과 같다 — 구조 오류와 모순은 거부하고 정렬·반올림만 복구한다.

### 3.5 영향 범위

`model.ts`, `validate.ts`, `song-schema.ts`, `expand.ts`, `demo-song.ts`, `testing/builders.ts`(곡 조립 도구가 `progression`을 채운다), 그리고 그 테스트. `chords.ts`·`patterns.ts`(카탈로그·스냅샷)는 **바뀌지 않는다** — 패턴 id는 불변이다. 엔진·스케줄러·샘플 계층은 `TrackEvents[]`만 읽으므로 바뀌지 않는다. 새 데모 곡은 4트랙이다(옛 데모의 멜로디 `notes` 트랙은 UI가 다루지 못하므로 뺀다. `notes` 클립 경로는 단위 테스트가 직접 만든 곡으로 계속 검증한다).

## 4. 순수 편집 함수 (`lib/score/edit.ts`)

UI는 이 함수만 부르고, 규칙은 모두 여기에 둔다(훅·컴포넌트에 두지 않는다). 모든 함수는 새 `Song`을 돌려주고 **아무것도 안 바뀌면 같은 참조를 돌려준다**(실행취소가 빈 칸을 쌓지 않는다). 위치·길이는 격자(`SNAP_TICKS = 960`)에 스냅한다. 모든 결과는 `validateSong`을 통과해야 한다.

상수: `SNAP_TICKS = 960`, `DEFAULT_CLIP_TICKS = 1920`, `MIN_BARS = 1`, `MAX_BARS_UI = 64`(모델 상한 500과 별개인 UI 한도).

**진행**
- `setChord(song, index, chord)` — 같은 코드면 no-op.
- `splitSegment(song, tick)` — 스냅한 `tick`이 한 구간 안에 있고 양쪽이 반마디 이상일 때만, 같은 코드의 두 구간으로 쪼갠다. 아니면 no-op.
- `moveBoundary(song, index, tick)` — 구간 `index`와 `index+1` 사이 경계를 옮긴다. 스냅하고 양쪽 반마디 이상이 되도록 **범위로 클램프**한다. 변화가 없으면 no-op.
- `mergeSegments(song, index)` — `index`와 `index+1`을 **왼쪽 코드로** 합친다. 구간이 하나뿐이면 no-op.

**클립**(트랙은 `trackId`, 클립은 `clipId`로 지정)
- `addClip(song, trackId, startTick)` — 스냅한 위치에 새 패턴 클립을 만든다. 길이는 `DEFAULT_CLIP_TICKS`와 "다음 클립 시작 또는 곡 끝까지의 빈 공간" 중 작은 값이고, 반마디 미만이면 no-op. 패턴은 그 악기의 카탈로그 첫 패턴이다. 클립 id는 결정적이다(트랙 안 최대 번호 + 1).
- `moveClip(song, trackId, clipId, startTick)` — 스냅한 뒤 이웃 클립을 **넘지 않도록** 빈 공간 안으로 클램프한다. 곡 밖으로 못 나간다.
- `resizeClip(song, trackId, clipId, lengthTicks)` — 스냅, 최소 반마디, 최대는 다음 클립 시작 또는 곡 끝까지. `notes` 클립을 줄이면 밖으로 나가는 음은 자르고 끝 이후에 시작하는 음은 버린다.
- `removeClip`, `setClipPattern(song, trackId, clipId, patternId)` — 악기에 맞지 않는 패턴 id는 던진다(UI는 맞는 목록만 보여 준다), `setTrackPattern(song, trackId, patternId)` — 그 트랙의 모든 패턴 클립에 적용.

**곡 전체**
- `setBars(song, bars)` — `MIN_BARS..MAX_BARS_UI`로 클램프. 늘리면 마지막 진행 구간을 늘린다. 줄이면 새 끝을 넘는 클립은 자르고(끝 이후에 시작하는 클립은 삭제) 진행도 새 끝에서 자른다.
- `setTempo(song, bpm)` — `MIN_TEMPO..MAX_TEMPO`로 클램프, 정수.

**테스트:** 함수마다 정상·경계·no-op(같은 참조)·거부 경로를 확인하고, **임의의 편집 열**(시드 고정 난수)을 수백 번 적용한 뒤 매번 `validateSong === []`을 확인하는 속성 테스트를 둔다.

## 5. 상태 계층 (`state/`)

- `StudioProvider`가 `Engine` 하나와 React 상태(곡, 선택, 재생 여부, 메시지)를 소유한다. 실행취소는 `lib/score/history.ts`를 쓴다(`commit`/`replaceWithoutHistory`/`undo`).
- 편집 핸들러는 `lib/score/edit.ts` 함수를 `commit`으로 부른다. 곡이 바뀔 때 정지 중이면 `engine.setSong(song)`으로 맞춘다(`false`는 재생 중이라는 뜻이므로 편집 자체를 막는다). 한 번의 드래그는 실행취소 한 칸이다.
- 재생 여부는 `engine.play()`가 `{status:"playing"}`으로 끝났을 때만 켠다(샘플 로딩 대기 동안 `isPlaying()`은 참이므로 쓰지 않는다). `not-ready`는 실패한 악기 이름을 메시지로 보여 준다. 곡 끝 자동 정지(`onStop`)와 수동 정지 모두 엔진을 최신 곡·템포로 다시 맞춘다.
- 플레이헤드는 `requestAnimationFrame`에서 `engine.currentTick()`을 읽어 DOM에 `transform`만 쓴다(`useState` 금지). 마디·박 표시만 10Hz로 샘플링한다.
- **자동 저장:** 편집 뒤 300ms 디바운스로 `localStorage`(`bandline:song:v3`)에 곡 JSON을 저장한다. 시작할 때 `parseSong`으로 읽고, 실패하거나 키가 없으면 데모 곡으로 시작한다(깨졌으면 한 줄 안내, 복구했으면 복구 내용 안내). `localStorage`를 못 쓰는 환경은 조용히 건너뛰고 한 번만 알린다.
- 저장·읽기의 순수 부분(직렬화, `parseSong` 결과 처리)은 `lib/score/`에, 브라우저 `localStorage` 접근은 `state/`에 둔다.

```text
┌ Bandline ─ ▶재생/■정지  마디 3·박 2  템포 ─○─ 120  ☐메트로놈  ↶되돌리기  [샘플 상태] ┐
├────────┬──────────────────────────────────────────────────────────┤
│        │  1     2     3     4     5     6     7     8   [＋마디]  │
│ 코드   │ [  C   ][  Am  ][ F ][ G ][  C   ][  Am  ][  F   ][ G7 ] │
│ 피아노 │ [arp 8th·········][arp 8th······]                          │
│ 기타   │ [strum ··········]                                         │
│ 베이스 │ [root ♩ ·········][root ♩ ·······]                         │
│ 드럼   │ [basic rock ······························]                │
└────────┴──────────────────────────────────────────────────────────┘
```

- **코드 레인:** 구간 클릭 → 코드 선택 팝오버(근음 12 × 종류 5). 경계선 드래그 → 길이 변경, 구간 안 버튼으로 분할, 이웃과 합치기.
- **트랙 레인:** 빈 곳 클릭 → 1마디 클립(`addClip`). 본문 드래그 → 이동, 오른쪽 가장자리 드래그 → 길이, `Delete` → 삭제. 클립 클릭 → 패턴 선택 팝오버와 "이 트랙 전체에 적용". `notes` 클립은 이동·길이·삭제만 되고 패턴 팝오버는 없다.
- **드래그:** 포인터 이벤트(캡처). 드래그 중에는 편집 함수를 **미리보기**로 적용해 결과 위치를 보여 주고, 놓을 때 한 번 커밋한다. `Esc`는 취소. 제자리에 놓으면 아무것도 기록되지 않는다.
- **키보드:** `Space` 재생/정지, `Ctrl+Z` 되돌리기, `Delete` 선택한 클립 삭제, `Esc` 팝오버 닫기·드래그 취소. 입력 요소에 포커스가 있으면 단축키를 가로채지 않는다.
- **상단:** 재생/정지, 위치, 템포, 메트로놈, 되돌리기, 악기별 샘플 상태와 실패 시 재시도(소리 확인 화면의 기능을 옮긴다), 메시지 줄.
- 마디 추가·삭제(`setBars`, 상한 64). 재생 중에는 편집 컨트롤이 비활성화되고 이유가 표시된다.
- 좌표 계산(틱↔픽셀, 스냅, 드래그 결과)은 순수 함수(`geometry.ts`)로 분리해 단위 테스트한다. 테마는 Tailwind 다크 톤이며 `.claude/rules/ui-conventions.md`를 따른다(최소: 컨트롤은 실제 `<button>`, 키보드로 탭 이동 가능, 숫자는 `font-mono`).
- `/`가 이 화면이 된다. `components/verify/`와 그 테스트는 삭제한다.

## 7. 테스트 전략

- **규칙은 `lib/`의 순수 함수에서 테스트한다**(§4, §3). 이 계층이 가장 두껍다. 변이 검증(코드를 일부러 망가뜨려 테스트가 실패하는지)을 핵심 규칙에 한다: 클램프, 스냅, 겹침 방지, 진행 불변식, no-op 같은 참조.
- **펼치기:** 진행이 있는 곡에서 같은 패턴 클립이 코드 구간마다 다른 음높이를 내는지, 마디 중간 코드 변경, 드럼은 진행 무관, 베이크 결과와 펼침 결과 동치(`expandSong(baked) == expandSong(original)`).
- **컴포넌트(jsdom):** 핵심 상호작용마다 테스트 — 클립 추가/이동/길이/삭제, 코드 변경·분할·합치기, 패턴 선택, 되돌리기, 재생 중 편집 비활성, 플레이 결과별 UI 상태(`playing`만 정지 버튼), 자동 저장·복원·깨진 데이터 처리. 지금까지 이 계층에서 결함이 반복해서 나왔으므로 **UI 상태가 엔진 상태와 어긋나는 경로**(재생 대기, 자동 정지, 거부된 `setSong`)를 특히 테스트한다. jsdom에는 레이아웃이 없으므로 좌표는 `getBoundingClientRect` 스텁과 순수 `geometry.ts`로 다룬다.
- **소리는 자동으로 검증되지 않는다.** 완료 기준에 "직접 듣기"를 넣고, 듣지 못했으면 명시한다.

## 8. 오류 처리

- 샘플 로딩 실패: 기존대로 악기별 상태와 재시도, `not-ready` 메시지.
- 저장 데이터 깨짐·옛 버전: 데모 곡으로 시작하고 안내한다. 편집은 항상 유효한 곡에서만 일어난다.
- 불가능한 편집(공간 부족, 최소 길이 미만): 아무 일도 일어나지 않고 기록되지 않는다(no-op). 에러 메시지를 띄우지 않는다.
- 편집 함수에 악기와 맞지 않는 패턴 id가 들어오는 것은 프로그래머 오류이므로 던진다.

## 9. 완료 기준

1. `pnpm lint`, `pnpm check-types`, `pnpm test`, `pnpm build` 통과.
2. §3·§4의 모든 규칙에 테스트가 있고, 임의 편집 열 속성 테스트가 통과한다.
3. §7의 컴포넌트 시나리오가 테스트로 덮이고, 핵심 보호 테스트는 변이 검증을 거쳤다.
4. `pnpm dev`로 `/`에서 직접 조립하고 들어 봤다(못 했으면 그렇게 명시한다): 코드를 바꾸면 모든 반주가 따라오는지, 마디 중간 코드 변경이 자연스러운지, 드래그가 격자에 붙는지, 되돌리기가 한 동작씩인지, 새로고침 뒤 복원되는지.
5. `AGENTS.md`, `README.md`, `docs/known-gaps.md`, 기존 spec(§3 모델)을 v3와 새 화면에 맞게 갱신한다. 문서가 코드를 따라오지 못한 전례가 있다.

## 10. 알려진 위험과 결정한 기본값

- **이미 병합·리뷰한 모델을 고친다.** 영향 범위(§3.5)가 넓다. 계획의 첫 작업으로 모델 v3 이행을 단독으로 끝내고 그 위에 편집 함수와 UI를 쌓는다.
- **UI 한도(64마디)와 모델 상한(500마디)은 별개다.** 자동 저장은 자기 곡만 읽지만 `parseSong`을 거친다. 파일·링크가 붙기 전에 개수 상한과 펼친 이벤트 예산 검사가 필요하다는 기존 과제(`docs/known-gaps.md`)는 그대로 남는다.
- **마디 중간 코드 변경은 이어서 울린다.** 이미 울리기 시작한 음은 높이를 유지하고 다음 스텝부터 새 코드다. 들어 보고 어색하면 패턴 쪽이 아니라 이 규칙을 조정한다.
- **드럼과 화음 악기의 패턴 목록이 다르다.** 팝오버는 `patternsFor(instrument)`만 보여 준다.
- 실행취소 한도는 기존 `HISTORY_LIMIT`(50)을 쓴다.
