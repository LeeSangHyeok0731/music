# 알려진 공백

지금 이 저장소에서 **검증되지 않는 것**과 **미뤄진 작업**을 모아 둔다. 새 세션을 시작하는 사람(또는 에이전트)이 "무엇을 믿어도 되고 무엇을 직접 확인해야 하는지" 알기 위한 문서다.

기능 목록(무엇이 아직 없는지)은 `AGENTS.md`에 있다. 여기는 **품질과 검증**에 대한 것이다.

최종 갱신: 2026-11-21 (블록 조립 편집 화면과 곡 모델 v3 — 하위 프로젝트 2a)

## 1. 정적 검사는 소리를 증명하지 않는다

`pnpm lint` · `check-types` · `test` · `build`가 전부 통과해도 **소리가 나는지는 아무것도 말해주지 않는다.** 재생·타이밍·악기를 건드렸으면 `pnpm dev`로 직접 들어야 한다.

`pnpm build`만은 예외적으로 의미가 있다 — 모듈 스코프에서 `AudioContext`를 만들면 서버 렌더링 중에 평가되어 여기서 깨진다.

## 3. 샘플 팩은 있지만 듣지 않았다

`public/samples/`에 CC0 팩이 커밋돼 있다: 피아노(VCSL Steinway B, 11존), 기타(Karoryfer Emily Guitar, 8존), 베이스(Karoryfer Growly Bass, 7존), 드럼(Virtuosity Drums의 킥·스네어·닫힌 하이햇). 총 2,268,016바이트(악기당 1.5MiB·총 5MiB 상한은 `budget.test.ts`가 지킨다). 출처·고정 커밋·가공 내용은 `public/samples/LICENSES.md`이고, 둘 다 `pnpm build:samples`(`scripts/build-sample-pack.mjs`)가 만든다 — 고정 커밋의 LICENSE가 CC0 1.0 Universal이 아니면(GitHub API SPDX도) 빌드가 멈춘다. 같은 캐시로 다시 돌리면 WAV·manifest가 바이트 단위로 같다.

남은 것:
- **청취**(2절). 소리가 좋다는 근거는 아직 없다.
- **어쿠스틱 기타가 없다.** CC0 어쿠스틱 기타 단음 샘플을 찾지 못해 기타 트랙은 일렉트릭 기타 직결 녹음이다.
- **베이스 음역 매핑.** Growly Bass의 파일 이름(과 SFZ의 `pitch_keycenter`)은 실제로 울리는 음보다 한 옥타브 위다(`e2_f_rr1.wav`는 E1 ≈ 41Hz). 매니페스트의 `centerPitch`는 실제로 울리는 음이라 MIDI 40은 E2(82Hz)로 난다. 데모 곡의 베이스(옥타브 2, MIDI 36~47)가 너무 높게 들리면 곡 쪽 옥타브를 고칠 일이지 매니페스트를 옥타브 올릴 일이 아니다 — `pack.test.ts`가 막는다.
- 셈여림 층·라운드로빈은 하나씩만 쓴다(같은 음을 연타하면 같은 소리). 음 길이가 샘플 길이(재생 속도로 보정한 뒤)보다 길면 샘플 끝에서 소리가 끝난다.

## 4. 자동 테스트는 jsdom까지다 — 실제 브라우저 동작은 증명하지 못한다

`vitest.config.mts`가 `lib/**`는 `node`, `state/**`·`components/**`는 `jsdom`으로 돈다. `components/studio/**`와 `state/**`에는 jsdom 컴포넌트·통합 테스트가 많다(`Studio.integration.test.tsx`가 가짜 엔진·뱅크·저장소 위에서 사용자 입력으로 전체 흐름을 돈다). 하지만 jsdom에는 레이아웃과 실제 `PointerEvent`가 없어서, 좌표는 `getBoundingClientRect` 스텁으로, 포인터는 `components/studio/testing/pointer.ts` 헬퍼로 흉내 낸다. 그래서 **실제 브라우저에서의 포인터 캡처·클릭 삼키기·`lostpointercapture` 순서·`:focus-visible`·스크롤·팝오버 위치·드래그 느낌은 자동 테스트가 보장하지 않는다.** 통제자가 Chrome에서 한 번 스모크 점검했다(9절). 옛 설계의 심각한 결함은 전부 이 계층에서 나왔다는 점을 기억한다 — **규칙이 든 로직은 훅·컴포넌트에 두지 않고 `lib/`의 순수 함수로 뺀다**(편집 규칙은 `lib/score/edit.ts`). 한 번 놓친 사례: 5px 임계값 뒤에 포인터를 캡처하면 마우스(암묵 캡처 없음)로 8px 핸들을 끌 수 없는데, 모든 테스트가 눌린 요소에 이벤트를 직접 쏘아 jsdom에서는 보이지 않았다(`ui-conventions.md` 인터랙션 절).

## 5. CI 초록이 Windows 동작을 보장하지 않는다

저장소는 LF로 커밋하지만 Windows 체크아웃에서는 `core.autocrlf`가 CRLF로 바꾼다. CI는 `ubuntu-latest`라 LF로 받는다.

**파일 내용을 정규식으로 파싱하는 테스트는 `\r?\n`을 써야 한다.** `\n`만 쓰면 CI는 통과하고 Windows 로컬만 깨진다. 새로 만든 파일은 작성 직후에는 LF라 그 세션에서는 통과하고, `git checkout`으로 브랜치를 옮기는 순간 변환되어 깨진다. **작성한 세션에서는 절대 재현되지 않는다.**

## 6. 패턴은 4/4 기준이다

`lib/score/patterns.ts`의 패턴은 틱 단위이고 4/4 한 마디(1920틱, `BAR_4_4`)를 기준으로 만들었다. 스키마는 다른 박자표도 받는다 — 분자 1~32 정수(`MAX_BEATS_PER_BAR`), 분모 1·2·4·8·16·32(`BEAT_UNITS`). 그런 곡에서는 패턴이 자기 길이로 반복되어 마디선과 어긋난다. 편집 UI가 4/4만 제공하는 동안은 문제가 되지 않는다. 다른 박자를 지원하려면 패턴 길이를 박 단위로 다시 정의해야 한다(새 패턴 id로).

## 7. 이월된 결정과 한계

구현 중 리뷰에서 나왔지만 이번 범위에서 고치지 않기로 한 것들이다. 해당 영역을 만지기 전에 읽는다.

1. **`isPlaying()`이 샘플 로딩 대기 중에도 `true`다.** `play()`는 첫 await 전에 `playing`을 올리고, 컨텍스트 재개와 샘플 준비(`ensureReady`)를 기다리는 동안 내리지 않는다. 그 구간에서 `setSong()`도 `false`다. 느린 네트워크에서는 몇 초씩 간다. 편집 UI는 이 구간을 "재생 중"으로 표시하면 안 되고, `setSong`의 `false`를 반드시 처리해야 한다. 편집 화면(`StudioProvider`)은 `play()`가 `{status:"playing"}`로 끝난 뒤에만 `playing`으로 보고(그 전은 `pending`: 편집 불가, "샘플을 불러오는 중…"), 로딩 진행 표시는 없다. 3번의 타임아웃 부재와 합치면 대기가 끝나지 않을 수 있다: `browserFetchBytes`(`fetch`에 타임아웃·`AbortSignal` 없음)가 영영 끝나지 않으면 `Engine.play()`가 끝나지 않고 `isPlaying()`이 `true`로 남는데, `pending` 동안에도 정지 버튼이 보이고 Space도 정지한다(`StudioProvider.stop()`이 세션 토큰을 올려 옛 `play()`의 늦은 결과를 버리고 화면은 `idle`로 돌아와 다시 편집된다). 그래서 새로고침 없이 빠져나올 수는 있다. 다만 받기 자체에는 여전히 타임아웃이 없어 다시 재생하면 같은 악기를 기다릴 수 있다. 고칠 계획: `browserFetchBytes`에 타임아웃(예: `AbortSignal.timeout`)과 로딩 진행 표시.
2. **`SampleBank`를 주입하지 않은 `Engine`은 저마다 뱅크를 만든다**(생성자 기본값 `defaultSampleBank()`). `StudioProvider`의 `createRealDeps`는 뱅크 하나를 만들어 엔진에 넘기지만, 개발 모드 StrictMode에서는 `useState(createDeps)` 초기화가 두 번 돌아 prefetch도 두 번 일어난다(프로덕션 영향 없음).
3. **`SampleBank`의 실패 보고가 거칠다.** 실패는 악기 단위로만 알린다(`error` 상태, `not-ready`의 `failed` 목록) — 이유 문자열이 없다. 구독 리스너는 상태를 알리는 도중에 동기로 불리므로 **던지면 안 된다**(잡아 주지 않는다). `fetchBytes`가 영영 끝나지 않으면 그 악기는 `loading`에 머문다(타임아웃 없음).
4. **드럼은 샘플 자체의 끝 페이드에 기댄다.** 드럼은 음높이 보정 없이(`playbackRate` 1) 샘플이 끝날 때까지 울리는 원샷이고 엔진은 엔벨로프를 걸지 않는다. 팩의 드럼 파일은 꼬리를 잘라(킥·스네어 0.5s, 하이햇 0.3s) 마지막 40ms를 페이드했다(마지막 샘플 0을 `pack.test.ts`가 확인). 끝에서 클릭이 나는지, 잘린 꼬리가 부자연스러운지는 귀로 확인하지 않았다.
5. **곡 파일 검증의 다듬지 않은 부분.** zod 오류 메시지는 영어이고 `validateSong` 메시지는 한국어이며 경로 표기도 다르다(`tracks.0.clips` vs `tracks[0].clips[0]`). 곡 파일의 모르는 키는 조용히 버려진다. 트랙·클립·음·코드 진행 구간 개수와 id 길이에 상한이 없다(`tracks`·`progression`은 `.min(1)`만 있다). 비용은 6번의 확장 이벤트 수로 재야 하고, 상한은 6번과 함께 **신뢰할 수 없는 입력이 `parseSong`·`Engine`에 닿기 전에** 넣는다.
6. **곡 크기에 상한이 없고, 진짜 비용은 틱이 아니라 확장된 이벤트 수다.** `bars ≤ 500`과 박자표 한도가 틱 수를 간접적으로 막을 뿐이다(최악 500마디 × 32박 × 1920틱 = 30,720,000틱, 분모 1일 때). 카탈로그 패턴은 모두 1920틱이고 가장 촘촘한 것(`drum-basic-rock`, `guitar-strum-quarter`)이 12스텝이라, 그 최악 곡에서 전체 길이 코드 클립 하나(JSON 약 150바이트)가 트랙당 16,000 × 12 = 192,000 이벤트로 펴진다. `tracks`·클립·음 개수에 상한이 없으므로 트랙 100개면 약 1,900만 개의 `ScheduledNote`를 `Engine` 생성자·`setSong`의 `expandSong`이 메인 스레드에서 동기로 만든다 — `parseSong` 자체는 값싸게 `ok`를 돌려준다. 지금 신뢰할 수 없는 입력이 닿는 길은 자동 저장 복원(`loadSong` → `parseSong`)뿐이고, 그것은 사용자 자신의 브라우저 저장값이다. 하지만 파일 열기 UI(하위 프로젝트 2b)나 링크(3)가 생기면 남의 입력이 닿는다. 그러니 개수 상한과 **확장 이벤트 예산 검사**를 `parseSong` 안에 넣어야 한다 — 펴지 않고도 Σ ceil(클립 길이 / 패턴 길이) × 스텝 수로 계산된다 — 파일 열기든 링크든 신뢰할 수 없는 입력이 `parseSong`·`Engine`에 닿기 **전에**.
7. **곡 편집, 템포 변경, 정지, 곡 끝 자동 정지가 `engine.setSong`을 부르고(`StudioProvider`의 동기화 effect), `setSong`은 `prefetch`를 부른다.** 그래서 정지 중에는(재생 중에는 `setSong`이 `prefetch` 전에 `false`로 끝난다) `error`인 악기를 의도치 않게 다시 받기 시작한다. 편집 화면에서 "파일을 막고 다시 시도"를 확인할 때 이 부작용이 결과를 흐릴 수 있다.
8. **계획 Task 15의 사람 몫이 남아 있다.** 팩 조달·형식 결정(16비트 PCM 모노 22.05kHz WAV)·예산 테스트는 끝났고, 청취가 남았다(2절·3절). Safari는 지원 대상이 아니다.

## 8. 문서가 코드를 따라오지 못한 전례

- `README.md`가 "스캐폴드 단계"라고 말하는 동안 실제로는 편집·재생·저장이 다 되고 있었다
- `AGENTS.md`의 "아직 없는 것" 목록에 방금 만든 기능이 남아 있었다
- 설계 문서의 `file:line` 인용이 리팩터링 후 어긋났다

기능을 하나 끝내면 `AGENTS.md`와 `README.md`가 여전히 사실인지 확인한다. 특히 `AGENTS.md`는 에이전트가 매 세션 자동으로 읽으므로, 틀린 내용이 그대로 다음 작업의 전제가 된다.

곡 파일 형식 문서(`docs/song-file-format.md`)와 그것을 지키던 `lib/score/format-doc.test.ts`는 v1 모델과 함께 삭제했다. v3의 파일·링크 형식은 파일 열기·저장(2b)·공유(3) 하위 프로젝트의 spec에서 새로 쓴다. 지금은 문서를 테스트로 지키는 장치가 없다.

## 9. 편집 화면(하위 프로젝트 2a)의 알려진 공백

**통제자의 Chrome 스모크 점검(소리 없이)으로 확인된 것:** 첫 화면 레이아웃(눈금·코드 레인 C Am F G7·4트랙 클립·상단 바·샘플 상태·마디 ±), 코드 팝오버(포털, 잘림 없음)·근음 변경·Esc 닫기, 8px 길이 핸들 실제 마우스 드래그, 빈 칸 클릭 클립 추가, 클립 몸체 드래그 이동(스냅, 드래그 뒤 팝오버 안 열림 = click 삼키기), Delete 삭제·Ctrl+Z 복원, Space 재생 시작·정지(플레이헤드 이동, 재생 중 편집 불가 안내, 정지 시 위치 복귀), 자동 저장(v3)·새로고침 복원, 하이드레이션·콘솔 오류 없음, 마디 줄이기 안내. 개발 서버(StrictMode)에서도 이상 없었다. 이 점검 뒤 localStorage의 테스트 곡은 지웠다.

**모델·한도**
- **UI 한도 64마디 vs 모델 상한 500.** `setBars`는 `MIN_BARS..MAX_BARS_UI`로 클램프하므로 65~500마디로 불러온 곡에 호출하면 64로 잘라 클립·진행을 지운다. 그래서 `BarsControl`은 곡이 64마디를 넘으면 ± 버튼을 둘 다 막는다(마디 수를 못 바꾼다). 그 곡을 여는 것과 `setBars`를 뺀 편집은 막지 않는다(통합 테스트는 100마디 곡에서 두 버튼이 막혀 곡이 그대로인 것만 확인한다). 이 곡을 만드는 길은 지금 손으로 고친 저장값뿐이다.
- **신뢰할 수 없는 입력에 대한 상한이 없다.** `parseSong`에 트랙·클립·음·진행 구간 개수 상한과 펼친 이벤트 예산 검사가 없다(7절 5·6번). 자동 저장 복원이 `parseSong`을 거치지만 그 입력은 자기 저장값이다. **파일 열기·링크 전에** 반드시 넣는다.
- **4/4 전용 격자.** `BeatGrid`와 `geometry.ts`의 `tickToX`(1920틱 = 160px)는 박자표를 보지 않는다. 4/4가 아닌 곡(모델·`parseSong`은 허용)을 불러오면 격자선과 클립·플레이헤드가 어긋나고, 500마디 × 32박이면 격자선 DOM이 16,000개다. 큰 곡의 렌더 비용은 측정하지 않았다.
- 마디를 줄일 때 **빈 트랙 위에서 코드 진행 구간만 잘리면 안내가 없다**(`shrinkDiscardsClips`는 클립 손실만 센다). 되돌리기로 복구된다.
- 정렬되지 않은(손으로 고친) 곡에서는 `resizeClip`이 빈 공간이 반마디보다 좁으면 줄이기 요청에서도 길이가 늘어날 수 있다(`upper`가 이긴다). 정상 편집으로 만든 곡에서는 일어나지 않는다.

**자동 저장·복원**
- 키 `bandline:song:v3`. 저장된 곡을 읽지 못하면(깨진 JSON·옛 v2·`parseSong` 거부) 데모 곡으로 시작하고 안내를 띄우지만 **그 저장값은 첫 사용자 편집 전까지 덮어쓰지 않는다.** 첫 편집이 일어나면 데모 기반 곡이 저장되어 원본은 사라진다. 복원은 실행취소에 쌓이지 않는다.
- 저장은 편집 뒤 300ms 디바운스이고, 대기 중인 저장은 `pagehide`와 언마운트에서 즉시 flush된다. 저장소를 못 쓰거나 쓰기가 실패하면 안내는 생애 한 번뿐이고(이후 성공해도 다시 알리지 않는다), 다른 메시지가 떠 있으면 덮지 않는다.
- **탭 두 개를 열면 마지막 저장이 이긴다.** `storage` 이벤트를 처리하지 않아 탭 A가 저장한 곡을 탭 B가 모른 채, B의 첫 편집이 그 저장값을 통째로 덮어쓴다(A의 편집 손실). 한 탭에서만 편집한다.
- 복원이 `useEffect`라 저장된 곡이 있어도 데모 곡이 한 프레임 보인다(`useLayoutEffect`로 줄일 수 있다).
- 마디 줄임 안내("되돌리기로 복구할 수 있습니다")가 되돌린 뒤에도 남는다.
- 개발 중 Fast Refresh가 재생 중 엔진을 dispose하면 UI가 `playing`으로 남을 수 있다(개발 한정). StrictMode의 dispose된 엔진 재사용 안전성은 가짜 엔진 테스트로만 확인했다 — 가짜가 실제처럼 비종결 `dispose`를 모사한다(실제 `Engine.dispose`는 비종결). 개발 서버에서의 실제 동작은 스모크 점검에서 문제없었다.

**접근성·키보드**
- 최소 접근성이다: 컨트롤은 실제 `button`, 클립 본문·코드 구간은 Tab으로 닿고 Enter/Space로 선택·팝오버가 열리며, 단축키(Space·Ctrl/Cmd+Z·Delete/Backspace·Esc)가 있다. 그 이상은 없다.
- 클립 **길이 핸들과 코드 경계 핸들은 포인터 전용**이다(`role="separator"`이지만 키 처리·`aria-valuenow` 없음). **키보드로 클립을 옮기거나 길이를 바꿀 수 없다**(코드 경계도). 격자 드래그의 키보드 대안이 없다.
- 팝오버에 **Tab 트랩이 없다.** 팝오버가 `body` 끝에 포털로 붙어 Shift+Tab이 앵커로 안 돌아온다. 스크린 리더용 역할·이름은 최소(`dialog`+`aria-label`)다.
- 팝오버 안에서는 `Delete`가 무시된다(팝오버가 열린 동안 클립을 지우려면 Esc로 닫은 뒤). 단축키로 지운 뒤에는 포커스를 옮기지 않지만(`×` 버튼 경로는 이웃 클립으로 옮긴다) 경로가 다르다.
- Space는 키보드로 포커스된(`:focus-visible`) 버튼 위에서 네이티브 클릭에 양보한다. Esc로 팝오버를 닫고 포커스가 앵커로 돌아가 `:focus-visible`이 되면 그 상태의 Space가 팝오버를 다시 열 수 있다 — 브라우저에서 확인하지 않았다.
- 눌려 있는 동안(5px 임계 전) Esc가 선택·팝오버를 닫고 `pointerup`이 다시 선택하는 경우가 있다.
- 한글 IME에서 Ctrl+Z(물리 키 `KeyZ` 대체)와 Backspace의 브라우저 뒤로 가기 방지는 브라우저에서 확인하지 않았다.

**화면 완성도**
- 안내·알림 줄(메시지, "재생 중에는 편집할 수 없습니다", "샘플을 불러오는 중…")이 뜨면 본문이 약 22px 아래로 밀린다(레이아웃 시프트). 자리를 미리 잡는 편이 낫다.
- 마디 ± 버튼이 타임라인 오른쪽 끝에 작게 붙어 있어 눈에 잘 안 띄고 멀다.
- 팝오버는 아래로만 붙고 위로 뒤집지 않는다(아래 공간이 없으면 가려진다). 가로 클램프는 스크롤바를 포함한 `innerWidth`를 쓴다. 세로 스크롤도 팝오버를 닫는다(`fixed`라 정상).
- `aria-disabled` 버튼이 hover 스타일을 유지한다(cosmetic).

## 10. 수동 확인 체크리스트 (듣기)

`pnpm dev`로 `/`를 열고 귀로 확인한다. 하나라도 어색하면 "코드를 마디 중간에서 바꾸면 이어서 울린다"는 규칙(spec 10절)과 패턴 쪽 중 어디를 고칠지 정한다.

1. 재생해서 데모 곡(C Am F G7 반복)이 자연스럽게 들리는지 듣는다(8마디, 약 16초).
2. 정지 상태에서 둘째 코드 구간(Am)을 눌러 근음을 F로 바꾼다(종류는 유지돼 Fm). 재생해서 **피아노·기타·베이스가 모두 F 계열로 따라오는지** 듣는다. 드럼은 달라지지 않아야 한다.
3. 한 코드 구간을 팝오버의 "가운데에서 나누기"로 쪼개고 뒷절반의 코드를 바꾼다. **마디 중간에서 코드가 바뀌는 소리**가 끊기지 않고 새 코드로 이어지는지 듣는다. 이미 울리던 음은 높이를 유지한다.
4. 각 트랙의 클립 팝오버에서 패턴을 하나씩 골라 **악기마다 모든 패턴**을 들어 본다(피아노·기타·베이스·드럼 각각). "이 트랙 전체에 적용"도 한 번 써 본다.
5. **재생 중 템포를 바꾼다.** 박자가 튀거나 끊기지 않는지, 이미 예약된 음이 새 템포로 이어지는지 듣는다. 재생 중 코드·클립 편집은 막혀야 한다.
6. 정지했다가 다시 재생한다(곡 끝 자동 정지 뒤 재생 포함). 첫 소리가 정확히 곡 시작에서 나는지 듣는다.
7. 새로고침해서 편집한 곡(바꾼 코드·클립)이 그대로 복원되는지 보고, 복원된 곡을 재생해 같은 소리가 나는지 듣는다.
8. 마디를 줄여 클립이 잘리게 한 뒤 안내가 뜨는지 보고, 되돌리기(Ctrl+Z)로 원래 소리로 돌아오는지 듣는다.
9. 메트로놈을 켜고 끝까지 들어 박자가 밀리지 않는지 확인한다(2절 장시간 재생).

## 11. 최종 리뷰에서 나온 후속 후보 (고치지 않았다)

코드 리뷰에서 나왔지만 이번 범위에서 고치지 않은 것들이다. 각각 한 줄로 왜 중요한지 적는다.

**편집 규칙·드래그**
- 클립 드래그 커밋이 이미 클램프된 값(`active.result`)을 `moveClip`/`resizeClip`에서 다시 스냅해, 손으로 고친 정렬 안 된 곡에서는 커밋이 미리보기와 다를 수 있다. `useBoundaryDrag`는 원시 틱을 넘기고, 정렬 안 된 경계를 그냥 클릭만 해도 이동이 커밋된다. 정상 편집으로 만든 곡에서는 일어나지 않는다.
- `useBoundaryDrag`에 `buttons` 가드가 없다. 놓기를 놓친 유령 드래그가 다음 클릭에서 커밋될 수 있다(캡처를 `pointerdown`에서 잡아 위험은 낮다).
- 포인터 제스처 도중에도 Delete가 막히지 않는다. 곡은 안 바뀌고(미리보기는 시작 스냅샷에서 그려져 놓을 때까지 화면만 어긋난다) 시각적 문제뿐이다.
- 팝오버 열린 개수가 effect에서 등록돼, 첫 effect 직전 찰나의 누름은 세지 않는다(그 누름이 클립을 추가할 수 있다).
- `segmentIndexAt`이 NaN 틱에서 docstring이 약속한 `RangeError` 대신 `mid`를 돌려준다(검증된 곡에서는 도달 불가). `addClip(song, id, -0)`은 start가 `-0`이 된다(직렬화하면 0이라 무해). `addClip`의 "빈 공간 < 반마디" 분기는 정렬 안 된 이웃이 있어야 닿아 테스트가 없다.

**렌더·상태**
- `Studio`가 컨텍스트 전체를 구독해 재생 중 10Hz로 `Studio`·`BeatGrid`·`Ruler`·`BarsControl`·헤더가 다시 그려진다. 64마디에서는 무시할 수준이지만 불러온 500마디 × 32박 곡에서는 격자 노드가 약 16,000개다. 고치려면 `memo(BeatGrid)`, `memo(Ruler)`.
- `StudioProvider`의 엔진 동기화 effect가 `setSong`의 불리언 결과를 보지 않는다. 단계(`phase`) 게이트로 안전하다(개발 중 Fast Refresh 예외만). 나중에 주석이나 처리를 더한다.
- 이전 `not-ready`·`PLAY_FAILED` 메시지가 뒤이은 성공적인 재생·재시도에도 지워지지 않는다(마디 줄임 안내가 되돌린 뒤에도 남는 것과 같은 종류).
- 복원 안내 같은 `role="status"` 알림은 텍스트와 함께 삽입되면 스크린 리더가 확실히 읽지 않을 수 있다.

**테스트 공백**
- **실제 `Engine`과 `StudioProvider`를 `lib/audio/testing`의 가짜 Web Audio 위에서 함께 돌리는 테스트가 없다.** Engine↔Provider 이음매(비종결 `dispose` 뒤 재사용, 대기 중 `setSong`이 `false`, 대기 중 `stop`이 `superseded`)는 손으로 쓴 가짜 엔진(`state/testing/fake-deps.ts`)으로만 고정돼 있어 실제 엔진이 바뀌면 가짜가 못 따라간다. 후속으로 권장한다.
- `StudioProvider`의 "pagehide·타이머가 다시 쓰지 않는다" 언마운트 테스트가 약하다.

**기록**
- `Engine.setSong`의 docstring(`lib/audio/engine.ts`)은 "던지는 것은 패턴이 잘못된 곡뿐"이라고 하지만 v3에서는 `clipNotes`가 `chordAt`을 부르므로 진행이 곡을 덮지 않으면 `RangeError`, 잘못된 `quality`는 `chordPitch`에서 오류가 난다. `parseSong`·편집 함수가 막아 지금은 닿지 않는다. 엔진은 보호 영역이라 이번에 고치지 않았다 — 고칠 때 docstring도 함께 고친다.
