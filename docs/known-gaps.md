# 알려진 공백

지금 이 저장소에서 **검증되지 않는 것**과 **미뤄진 작업**을 모아 둔다. 새 세션을 시작하는 사람(또는 에이전트)이 "무엇을 믿어도 되고 무엇을 직접 확인해야 하는지" 알기 위한 문서다.

기능 목록(무엇이 아직 없는지)은 `AGENTS.md`에 있다. 여기는 **품질과 검증**에 대한 것이다.

최종 갱신: 2026-11-20 (코어 모델·샘플 엔진 재구상 직후)

## 1. 정적 검사는 소리를 증명하지 않는다

`pnpm lint` · `check-types` · `test` · `build`가 전부 통과해도 **소리가 나는지는 아무것도 말해주지 않는다.** 재생·타이밍·악기를 건드렸으면 `pnpm dev`로 직접 들어야 한다.

`pnpm build`만은 예외적으로 의미가 있다 — 모듈 스코프에서 `AudioContext`를 만들면 서버 렌더링 중에 평가되어 여기서 깨진다.

## 3. 실제 샘플 팩이 없다

`public/samples/`에는 커밋된 샘플이 없다(디렉터리 전체가 gitignore다). 지금 소리는 `scripts/gen-dev-samples.mjs`가 만든 개발용 톤뿐이다(음색 품질을 위한 것이 아니다). 남은 작업(계획 Task 15, 사람이 필요하다): CC0·퍼블릭 도메인 팩을 골라 `public/samples/LICENSES.md`에 출처와 라이선스를 적고, 첫 재생 총량 5MB 이내를 지키는 예산 테스트(`lib/audio/samples/budget.test.ts`, 아직 없음)를 만들고, `.gitignore`의 개발용 톤 줄을 지운다. 라이선스가 확인되지 않은 파일은 저장소에 넣지 않는다.

## 4. `state/`·`components/`의 자동 테스트는 이제 막 시작이다

`vitest.config.mts`가 `lib/**`는 `node`, `state/**`·`components/**`는 `jsdom`으로 돈다. 지금 컴포넌트 테스트는 `components/verify/VerifyScreen.test.tsx` 하나뿐이고 `state/`는 아직 없다. 편집 UI(하위 프로젝트 2)가 들어오면 옛 설계에서 심각한 결함이 전부 이 계층에서 나왔다는 점을 기억한다 — **규칙이 든 로직은 훅·컴포넌트에 두지 않고 `lib/`의 순수 함수로 뺀다.**

## 5. CI 초록이 Windows 동작을 보장하지 않는다

저장소는 LF로 커밋하지만 Windows 체크아웃에서는 `core.autocrlf`가 CRLF로 바꾼다. CI는 `ubuntu-latest`라 LF로 받는다.

**파일 내용을 정규식으로 파싱하는 테스트는 `\r?\n`을 써야 한다.** `\n`만 쓰면 CI는 통과하고 Windows 로컬만 깨진다. 새로 만든 파일은 작성 직후에는 LF라 그 세션에서는 통과하고, `git checkout`으로 브랜치를 옮기는 순간 변환되어 깨진다. **작성한 세션에서는 절대 재현되지 않는다.**

## 6. 패턴은 4/4 기준이다

`lib/score/patterns.ts`의 패턴은 틱 단위이고 4/4 한 마디(1920틱, `BAR_4_4`)를 기준으로 만들었다. 스키마는 다른 박자표도 받는다 — 분자 1~32 정수(`MAX_BEATS_PER_BAR`), 분모 1·2·4·8·16·32(`BEAT_UNITS`). 그런 곡에서는 패턴이 자기 길이로 반복되어 마디선과 어긋난다. 편집 UI가 4/4만 제공하는 동안은 문제가 되지 않는다. 다른 박자를 지원하려면 패턴 길이를 박 단위로 다시 정의해야 한다(새 패턴 id로).

## 7. 이월된 결정과 한계

구현 중 리뷰에서 나왔지만 이번 범위에서 고치지 않기로 한 것들이다. 해당 영역을 만지기 전에 읽는다.

1. **`isPlaying()`이 샘플 로딩 대기 중에도 `true`다.** `play()`는 첫 await 전에 `playing`을 올리고, 컨텍스트 재개와 샘플 준비(`ensureReady`)를 기다리는 동안 내리지 않는다. 그 구간에서 `setSong()`도 `false`다. 느린 네트워크에서는 몇 초씩 간다. 편집 UI는 이 구간을 "재생 중"으로 표시하면 안 되고, `setSong`의 `false`를 반드시 처리해야 한다. 지금 검증 화면은 `play()`가 `playing`을 돌려준 뒤에만 재생 중으로 표시하고, 로딩 진행 표시나 취소는 없다.
2. **`SampleBank`를 주입하지 않은 `Engine`은 저마다 뱅크를 만든다**(생성자 기본값 `defaultSampleBank()`). 검증 화면은 뱅크 하나를 만들어 엔진에 넘기지만, 개발 모드 StrictMode에서는 `useState` 초기화가 두 번 돌아 prefetch도 두 번 일어난다(프로덕션 영향 없음).
3. **`SampleBank`의 실패 보고가 거칠다.** 실패는 악기 단위로만 알린다(`error` 상태, `not-ready`의 `failed` 목록) — 이유 문자열이 없다. 구독 리스너는 상태를 알리는 도중에 동기로 불리므로 **던지면 안 된다**(잡아 주지 않는다). `fetchBytes`가 영영 끝나지 않으면 그 악기는 `loading`에 머문다(타임아웃 없음).
4. **드럼 샘플은 페이드 없이 끝난다.** 드럼은 음높이 보정 없이(`playbackRate` 1) 샘플이 끝날 때까지 울리는 원샷이다. 실제 샘플을 넣을 때 꼬리를 잘라 낸 파일이면 끝에서 클릭이 나는지 듣는다.
5. **곡 파일 검증의 다듬지 않은 부분.** zod 오류 메시지는 영어이고 `validateSong` 메시지는 한국어이며 경로 표기도 다르다(`tracks.0.clips` vs `tracks[0].clips[0]`). 곡 파일의 모르는 키는 조용히 버려진다. 트랙·클립·음 개수와 id 길이에 상한이 없다 — 공유 링크를 내기 전에 넣는다.
6. **곡 전체 틱에 직접적인 상한이 없다.** `bars ≤ 500`과 박자표 한도가 간접적으로 막을 뿐이다(최악 500마디 × 32박 × 1920틱 = 30,720,000틱, 분모 1일 때). 박자표 UI가 생기면 다시 본다.
7. **템포 슬라이더, 정지, 곡 끝 자동 정지가 `engine.setSong`을 부르고, `setSong`은 `prefetch`를 부른다.** 그래서 정지 중에는(재생 중에는 `setSong`이 `prefetch` 전에 `false`로 끝난다) `error`인 악기를 의도치 않게 다시 받기 시작한다. 검증 화면에서 "파일을 막고 다시 시도"를 확인할 때 이 부작용이 결과를 흐릴 수 있다.
8. **계획 Task 15가 남아 있다.** CC0 샘플 팩 조달, 샘플 파일 형식 결정, Safari 디코드 확인(2절·3절).

## 8. 문서가 코드를 따라오지 못한 전례

- `README.md`가 "스캐폴드 단계"라고 말하는 동안 실제로는 편집·재생·저장이 다 되고 있었다
- `AGENTS.md`의 "아직 없는 것" 목록에 방금 만든 기능이 남아 있었다
- 설계 문서의 `file:line` 인용이 리팩터링 후 어긋났다

기능을 하나 끝내면 `AGENTS.md`와 `README.md`가 여전히 사실인지 확인한다. 특히 `AGENTS.md`는 에이전트가 매 세션 자동으로 읽으므로, 틀린 내용이 그대로 다음 작업의 전제가 된다.

곡 파일 형식 문서(`docs/song-file-format.md`)와 그것을 지키던 `lib/score/format-doc.test.ts`는 v1 모델과 함께 삭제했다. v2의 파일·링크 형식은 공유 하위 프로젝트(3)의 spec에서 새로 쓴다. 지금은 문서를 테스트로 지키는 장치가 없다.
